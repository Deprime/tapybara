# Server: карта для разработчика и LLM

Hono на Bun, MySQL через Drizzle. Точка входа — `src/index.ts`: маршруты,
Telegram webhook, фоновые задания и `Bun.serve`. API имеет префикс `/api`.
Подробности клиента: [../web/README.md](../web/README.md).

| Путь                                  | Назначение                                                                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `src/controllers/`                    | Hono HTTP-маршруты и сериализация ответов; `authPageController.ts` — обмен токена, `authController.ts` — сессия/посещение/выход |
| `src/middlewares/`                    | `requireAuth.ts` — cookie-сессия API, `pageAuth.ts` — защита SPA, `mobileOnly.ts` — опциональное ограничение устройств          |

| `src/helpers/datetime.ts`, `utils.ts` | Unix-время, хеширование, определение HTTPS                                                                                      |

## Общая структура сервера

Код размещается по назначению, как в существующих модулях:

```text
src/
  index.ts                         # Подключение маршрутов и запуск фоновых заданий
  controllers/                     # HTTP и входящие webhook
    authController.ts              # Сессия и фиксация посещения
    telegramController.ts          # Входящий webhook бота
  middlewares/                     # Проверки входящих запросов
  repo/
    inactivityRepo.ts              # Работа напоминаний с MySQL
  helpers/
    telegram.ts                    # Исходящие сообщения через существующий bot.api
  jobs/
    inactivityReminders.ts         # Расписание и правила напоминаний
  scripts/                         # Команды, запускаемые вручную
  mocks/                           # Локальные dev-фикстуры
  templates/                       # HTML-страницы сервера
```

Новые SQL-запросы добавляются в `repo/`, HTTP-маршруты — в `controllers/`,
фоновые задания — в `jobs/`. `helpers/telegram.ts` отвечает только за проверку
и доставку сообщения; выбор получателей и повторные попытки остаются в задании.
Команды бота лежат в `packages/bot/src/`, схема БД — в `packages/db/src/schema.ts`.
Имена файлов следуют текущему camelCase; модульные тесты лежат рядом (`*.test.ts`),
интеграционные — в `test/`. Отдельного дерева `notifications/telegram` больше нет.

## Потоки

**Вход:** личный чат → `/login` → `${SITE_URL}/auth?token=...` → одноразовое
потребление токена → HttpOnly cookie `sid` → `/`. По умолчанию ссылка живёт
600 секунд, сессия — 30 дней. Новый вход заменяет прежнюю сессию. В БД хранится
хеш сессионного токена. `/api/auth/me` проверяет сессию, но не отмечает посещение.

**Разработка:** `bun dev` выставляет `DEV_LOGIN=true`; открывать
`http://localhost:5173/auth/dev-login`. При `NODE_ENV=production` этот маршрут
не подключается даже с DEV_LOGIN. Не включать dev-режим на публичном сервере.

**Посещение:** клиент вызывает `POST /api/auth/visit` при открытии или возвращении
во вкладку; нужна cookie-сессия, cross-origin браузерные запросы отклоняются.
Сервер пишет Unix-секунды в `users.lastSeenAt`, сбрасывает `inactivityReminderAt`.
Клиент не передаёт ни время, ни ID пользователя. Простое нахождение в открытой
вкладке, игровые запросы и команды бота время не обновляют.

**Напоминание:** при BOT_TOKEN подключается существующий grammY client, проверка
проходит при старте и каждые 5 минут. Выбираются посетившие приложение ≥24 часов
назад, без результата напоминания. Блокированные и dev-фикстура исключены.
Текст: «🦫 Капибары соскучились! Загляни в приложение и продолжи игру».
После подтверждения Telegram результат записывается
в MySQL; новый цикл начинается после посещения. Для старых пользователей отсчёт
начинается с первого посещения после миграции; одна регистрация `/start` не считается.

Ошибки 400/403 (недоступный получатель) закрывают текущий цикл до следующего
посещения. Временные ошибки повторяются следующим проходом, 429 учитывает
`retry_after`. Токен и содержимое транспортной ошибки в журналы задания не попадают.
При отсутствии BOT_TOKEN задание не запускается, остальной сервер работает.

Процесс рассчитан на **один постоянно работающий экземпляр**. Проходы не
перекрываются, hot reload дожидается завершения предыдущего задания. После обычного
рестарта сохранённый результат предотвращает повтор. Падение между доставкой
Telegram и записью MySQL может дать повтор: exactly-once здесь не гарантируется.
Возвращение во время уже отправленного сетевого запроса не может отозвать сообщение,
но не закрывает следующий цикл. Несколько реплик потребуют claim/lease в БД.

**Капибары:** таблица `units`, обязательное `name VARCHAR(20) NOT NULL`. `/start`
создаёт первую капибару с именем `Капибара #<id>` внутри транзакции; миграция 0006
присваивает такой же формат существующим. Имя идёт в `/api/units`, ответы collect,
интерфейс и `/balance`. API переименования отсутствует. Балансы в боте выводятся
из decimal-строк, длинный список разбивается на сообщения.

`units.skin_uuid` — `VARCHAR(28) NOT NULL DEFAULT ''`. Новая капибара получает
пустую строку, пока скин не назначен. Миграция 0008 заполняет существующие NULL
пустой строкой перед добавлением NOT NULL и сохраняет назначенные идентификаторы.
Поле пока не включено в ответ API юнитов.

## Запуск и проверки

`apps/server/.env` загружается Bun при запуске серверного workspace.
`packages/db/.env` загружается при запуске миграций; в обоих файлах нужен один
и тот же действующий `DATABASE_URL`. Файлы `.env` исключены из Git; `.env.example`
служит только шаблоном и не должен содержать настоящий `BOT_TOKEN` или секрет webhook.
После изменения окружения перезапустить сервер.

Для локального клиента отдельный `.env` не требуется: прокси Vite использует
`http://localhost:3000`, а `SITE_URL` сервера — `http://localhost:5173`.
Для команд бота нужен публичный HTTPS-адрес сервера в `BOT_WEBHOOK_URL` и
непустой `TELEGRAM_WEBHOOK_SECRET`. Команда `bun bot:set-webhook` регистрирует
этот адрес в Telegram; без публичного адреса входящие команды локальному серверу
не доставляются. Dev-login доступен независимо от webhook, но требует БД.

Успешная проверка `/api/health` содержит `database: connected`;
одного HTTP 200 недостаточно. Проверять и порт 3000, и прокси на 5173.

Из корня: `bun install`, настроить `apps/server/.env` по примеру и DATABASE_URL
для миграций в `packages/db/.env`. Создать MySQL-базу, применить `bun db:migrate`
до запуска новой версии. Для production остановить прежний сервер на время DDL:
новая колонка name сначала допускает NULL, затем заполняется и становится NOT NULL.
Применить все миграции по 0008 включительно.

```sh
bun dev
bun run --filter @capyberries/server check
bun run --filter @capyberries/bot check
bun test packages/bot/src/messages.test.ts
```

MySQL-тест запускается отдельно, чтобы импортируемый singleton DB получил тестовый
DATABASE_URL. Он проверяет миграции на существующих строках, ограничения name/skin_uuid,
регистрацию, авторизацию, production-запрет dev-login и напоминания с fake sender.
В PowerShell:

```powershell
$env:MYSQL_INTEGRATION='1'
$env:TEST_MYSQL_URL='mysql://test_user:test_password@127.0.0.1:3306'
bun test apps/server/test/integration.test.ts
```

Пользователю MySQL нужны права создать/удалить отдельную базу `tapybara_test_<uuid>`.
Тест принимает только локальный хост, создаёт уникальную БД и удаляет её в finally.
Реальные Telegram-сообщения не отправляются. Обычный запуск без MYSQL_INTEGRATION
пропускает этот тест; это не подтверждение миграции на реальной БД.
